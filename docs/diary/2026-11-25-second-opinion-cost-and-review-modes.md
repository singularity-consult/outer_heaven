# Diary: second-opinion gets a price per call and review modes

Goal: extend the `second-opinion` skill and its script with two things the owner asked for. First, a price in USD and DKK next to the token counts, because token counts alone are hard to relate to. Second, review modes beyond code and diff: architecture, app solution, product proposal and visual design, the last one with image input. Context: earlier the same day an architecture review of outer_heaven went through the lead and the reviewer, and Gemini answered with four procedural findings in single files and nothing about layering, role split or scaling.

## Step 1: Requirements and hand-off to the builder

**Author:** lead

### Prompt Context

**Verbatim prompt:** The task came from the main agent, which relayed the owner's two wishes in translation: (1) "I find it a bit hard to relate to token usage alone. Can it be combined with a price in USD or DKK?" (2) "The script clearly needs an architecture mode. Likewise it must be able to assess a complete product proposal, an app solution and a graphic design (Power BI report, website or app interface)." The rest of the main agent's brief gave prices read from Google's pricing page that day, a fixed exchange rate, the required live calls, and the limits (commit only, no push).
**Interpretation:** Turn the two wishes into concrete requirements, challenge what does not hold, hand the build to one builder, then run one architecture review of outer_heaven in the new mode with the same material as the earlier call, so the two answers can be compared.
**Inferred intent:** The owner wants to be able to judge whether a second opinion was worth its money, and to get reviews that answer at the level of the material: structure for an architecture, users and assumptions for a proposal, what the eye meets for a design.

### What I did

Fetched and confirmed that `origin/main` is `0492b68` at plugin version 0.20.1, that the highest tag is `v0.20.1`, and that the remote has no branch other than `main`. Created the branch `second-opinion-cost-and-review-modes` in the lead worktree. Read `skills/second-opinion/SKILL.md`, the script and the names of its 36 tests, `agents/reviewer.md`, `agents/lead.md`, and the requirements, material and answer of the earlier architecture call.

Checked Google's documentation for image input before writing any requirement about it, through a summarising fetch tool. The API reference for `generateContent` describes a Part with `inlineData`, a Blob with `mimeType` and `data`. The image guide lists PNG, JPEG, WEBP, HEIC and HEIF, a 20 MB limit on the whole request when images are inline, and 258 tokens per image tile. The reference calls `data` "raw bytes" and does not say base64; that is left for one live call to settle.

Wrote the requirements for the builder. The decisions I took on the owner's behalf, all of them reversible:

- Modes: `code` (default, unchanged on the wire), `architecture`, `solution`, `product`, `design`. Architecture and app solution stay two modes. They share a lot, but they ask different questions: architecture asks how one system is structured, solution asks whether a proposed solution meets a stated need end to end, including functions, data, security, operation and cost. The cost of the second mode is one prompt. Whether the two prompts give usefully different answers is not tested.
- Schema: code mode keeps its schema. The other modes add a `category` and an `evidence` field per finding, and a top-level `coverage` list with one item per rubric dimension (problems found, no problems found, or not assessable, each with a basis). The coverage list is aimed at the failure seen earlier: an answer that never touches the question asked, and a summary that praises without anything behind it.
- A neutral text channel, `--context`, so that text which is not a diff is not labelled as one.
- Price: a table in the script keyed on the resolved model version, dated, exact match only; a fixed dated DKK rate; both overridable; no network call for the rate. An unknown model gets tokens and the words "price unknown", never a guess.
- Images: every run with images is refused unless `--images-approved` is passed, whatever the path. The path guard cannot see what a picture shows, so a screenshot of a customer report saved in an owned repo would pass it. One narrow exception for agents: a synthetic test image generated by code from no real data.

### Why

The earlier call showed three gaps at once: a system prompt written for code, no neutral channel for extra text, and no instruction for the reviewer when the answer goes past the focus. That the prompt caused the procedural answer is not proven; the rerun in architecture mode with the same material is the test of that.

### What worked

The earlier call's requirements, material and answer were still on disk, so the comparison can use the same input.

### What didn't work

The image guide's inline example targets a different endpoint than `generateContent`, and the API reference page was cut off by the fetch tool before its end. The exact wire form for an image in `generateContent` is therefore taken from the Part and Blob reference, not from an example, and needs the live call.

### What I learned

The data guard is a path guard. For text that is a fair proxy, because text comes out of the repo it is checked against. For a picture it is not: where the file lies says nothing about what it shows.

### What was tricky

The requirement "images always need the owner's yes" collides with the requirement "confirm the image format in a live call". I resolved it with the synthetic-image exception and listed it as an open choice for the owner.

### What warrants review

The image rule and its exception; the decision to keep architecture and solution apart; the coverage list, which makes every non-code answer longer and so costs output tokens.

### Future work

None beyond the steps that follow in this file.

## Step 2: Cost, modes, context channel and images in the script

**Author:** builder

### Prompt Context

**Verbatim prompt:** (the summary paragraph of the lead's brief; the full requirements were in a separate file) "Summary of the job: extend skills/second-opinion/scripts/second_opinion.py (stdlib-only Gemini client) with (A) an estimated cost per call in USD and DKK from a dated price table, on stderr and in the JSON output; (B) a --mode option with code (default, byte-identical on the wire to today), architecture, solution, product and design, each non-code mode with its own system prompt and an extended response schema, plus a neutral --context text channel; (C) --images with an image data guard that refuses every image run unless --images-approved is passed; (D) updates to SKILL.md, agents/reviewer.md, agents/lead.md, README.md and plugin.json (0.21.0). Then tests, one single live call (the synthetic image test in section C6, nothing else), self-review, diary steps, and commits on the branch."
**Interpretation:** Build sections A to D of the requirements file exactly, keep a plain call unchanged on the wire and prove that with a test, make at most one live call, and report everything the requirements left open as a choice.
**Inferred intent:** A second opinion whose price can be read at a glance, and reviews that answer at the level of the material, without a new way for customer material to leave the machine.

### What I did

Before changing anything I pinned today's behaviour. A small script outside the repo ran the committed `second_opinion.py` in a fake owned repo with fixed arguments and hashed the `--dry-run` output: 3,194 characters, sha256 starting `81369e1c`. After the change the same run gives the same hash, and the test `test_default_call_sends_todays_body` holds it.

In `skills/second-opinion/scripts/second_opinion.py`:

- Modes. `MODE_DIMENSIONS` holds the rubric of each non-code mode, each dimension with the question it asks. One function builds the system prompt of a mode from a shared frame, and one builds its schema, so the `category` enum of a finding and the `dimension` enum of a coverage item come from the same list. `SYSTEM_PROMPT` and `RESPONSE_SCHEMA` are untouched and are what `code` mode sends.
- Context. `--context FILE|-` and `--context-label`, rendered as `### context: <label>` ahead of the diff and the files.
- Cost. `PRICE_TABLE` keyed on the resolved model version, with an effective-from date per row and tiers per row; `find_price`, `estimate_cost` and `cost_line` are pure and take the call date as an argument. The rate comes from `--usd-dkk`, else `SECOND_OPINION_USD_DKK`, else the constant.
- Images. Type from the magic bytes, `inlineData` parts after the text part, a size check, a display copy for `--dry-run`, and the image guard in `run()` next to the path guard.

The tests went from 34 to 79, all in `test_second_opinion.py`, none with a network call. Then SKILL.md, `agents/reviewer.md`, `agents/lead.md`, the two README lines and `plugin.json` (0.21.0). Before the version bump I fetched again: `origin/main` was still `0492b68` at 0.20.1, the highest tag `v0.20.1`, no other remote branch.

### Why

The pin came first because "unchanged on the wire" is the one requirement that a later edit can break without any test noticing, unless the reference is taken from the old code and not from the new.

### What worked

Building prompt and schema from one rubric list. The requirement that the category enum equals the coverage enum then holds by construction, and the test checks it against the ids written out in the requirements.

Keeping the cost functions pure with the date injected. Both sides of the price change at new year, and both sides of the 200,000-token tier, are plain assertions.

### What didn't work

The harness refused two commands, both before anything ran. First a compound Bash command that wrote files with a heredoc and then called git:

`This agent is isolated in the worktree ..., but this command is too complex to verify that it stays inside the worktree. Refusing to run it`

Then the same refusal for a `python - <<'EOF'` heredoc that would have patched the script. I moved each helper into a file in the session's scratch directory and ran it with one plain command.

`git show origin/main:.claude-plugin/plugin.json` failed in Git Bash on Windows:

`fatal: ambiguous argument 'origin\main;.claude-plugin\plugin.json': unknown revision or path not in the working tree.`

The shell rewrote the argument as a path list. The same command in PowerShell, with the argument in quotes, worked.

The lead's brief said the script had 36 tests. The run before my change said 34. I report the number the run gave.

### What I learned

`check_request_size(body_bytes, limit=MAX_REQUEST_BYTES)` binds the default when the function is defined, so a test that patches the constant changes nothing. The default is now `None` and the constant is read inside the function.

A refusal message is part of the behaviour. The path-guard text is the same as before, and the image text is a second section under the same `data guard: REFUSED` opening, so a run that fails both guards names both flags in one message.

### What was tricky

Deciding what counts as material. A design review can be an image and a requirement and nothing else, so the "no material" error had to stop firing when images are present, while still firing for a run with nothing at all.

The order of the two guards. Both are computed before anything is read, and one refusal lists both, so nobody fixes one flag only to meet the other refusal on the next run.

### What warrants review

- The prompts. `python skills/second-opinion/scripts/second_opinion.py --mode architecture --requirements-text x --context CLAUDE.md --dry-run` prints the full body. I read all five; only the design prompt has run live.
- The schema order in non-code modes: coverage and findings before summary and verdict. That is my choice, not the requirements'. Whether it changes answer quality is not measured.
- One line in each non-code prompt that the requirements did not ask for: a focus, when given, must be answered in the summary.
- The extension rule for images: the extension must agree with the magic bytes, and a file with no extension or an unknown one is refused.
- The cost object has one key more than the requirements list (`cached_tokens_at_full_rate`), and `reason` only when the price is unknown.

### Future work

The price rows other than `gemini-3.1-pro-preview` were not seen verbatim on Google's page; they need one look at the page. The table needs a new row the day the default alias moves to another model; until then the cost line says the price is unknown.

## Step 3: The one live call, self-review, and what it did not prove

**Author:** builder

### Prompt Context

**Verbatim prompt:** (from the requirements file, section C6) "One live call to confirm the format: generate a small synthetic PNG with stdlib (zlib + struct), for example a 200x120 image with a red left half and a blue right half, written inside the worktree in a temp file you delete afterwards (it must not be committed). Run design mode with a requirement such as \"A two-colour test card: the left half must be red and the right half blue\" and `--thinking-level low`, with --images-approved (synthetic image, see C4). Report: exit code, model version, the usage line and the cost line verbatim, and whether the answer shows the model saw the colours. That is the only live call you make."
**Interpretation:** Settle with one call whether `inlineData` with base64 data is the right wire form, and whether the extended schema is accepted.
**Inferred intent:** Do not ship an image feature whose request format is only an inference from a reference page.

### What I did

A script in the scratch directory built the PNG from `struct` and `zlib`: 200 by 120 pixels, 8-bit RGB, each row one filter byte, 100 red pixels and 100 blue pixels. 655 bytes, from no data at all. I opened the file to check it was a valid picture, ran the call as a dry run and read the body, then made the call:

`python skills/second-opinion/scripts/second_opinion.py --mode design --requirements-text "A two-colour test card: the left half must be red and the right half blue." --focus "Which colour fills the left half and which fills the right half?" --images synthetic_test_card.png --images-approved --thinking-level low`

Exit code 0. stderr:

```
data guard: images released by --images-approved (inline data):
  - image 1: synthetic_test_card.png (655 bytes, image/png)
request: model=gemini-pro-latest mode=design prompt_chars=268 images=1 thinking_level=low
model version: gemini-3.1-pro-preview
usage: promptTokenCount=1819 thoughtsTokenCount=0 candidatesTokenCount=321 totalTokenCount=2140
cost (estimate): 0.0075 USD = 0.05 DKK | prices as of 2026-11-25 (table), tier <=200k | 1 USD = 6.8178 DKK (fixed, 2026-11-24)
```

The answer had six coverage items, one per design dimension: `task_support` said no problems found, the other five said not assessable, each with a basis such as "There is no text or data to read". No findings, verdict approve. The summary said the card shows red on the left half and blue on the right half. I deleted the image and checked `git status`: it was gone and had never been staged.

Then the self-review: I read the whole diff against the requirements, ran the 79 tests, ran a dry run per mode, and searched every changed file for long dashes, the two banned hedging words and non-ASCII characters.

### Why

The reference page calls the field "raw bytes" and gives no JSON example for this endpoint. One accepted call is the cheapest proof of the wire form.

### What worked

The call was accepted on the first attempt: base64 in `data`, `mimeType` beside it, the image part after the text part, together with the extended schema and a thinking level. The coverage list did what it was built for: five honest "not assessable" answers on a picture with nothing in it to assess, where a free-text answer could have filled the space.

### What didn't work

The call does not prove that the model read the pixels. The requirement text named red on the left and blue on the right, and the answer named the same. A model that never looked at the image and repeated the requirement would have written the same summary. I saw this only when I read the answer; the test as specified could not tell the two cases apart, and I had no second call to spend. The token count does not settle it either: 1,819 prompt tokens cover the system prompt, the schema, the text and the image together, and the script does not print a per-modality split.

Self-review found one error in my own documentation. I had written in SKILL.md that four of the six coverage items said not assessable; the answer on disk says five. Corrected before commit.

### What I learned

A format test whose expected answer is written in the prompt tests the format and nothing more. To test that an image is seen, the image must hold something the text does not say, or something that contradicts it.

With thinking level low, this call reported 0 thought tokens. One call on one tiny prompt; it says nothing about a real review.

### What was tricky

Wording the result. "HTTP 200 and a sensible answer" reads like "it works", and for the wire format it does. For vision it is unproven, and SKILL.md now says so in those words, with the test that would settle it.

### What warrants review

- The image rule in SKILL.md and `agents/reviewer.md`, and the exception for a synthetic image, which is the rule this call ran under.
- The section "What is verified live, and what is not" in SKILL.md: check that it claims no more than this step shows.
- The cost line of this call rests on the one price row that was seen verbatim.

### Future work

One call with an image that contradicts its requirement text (for example a card in two other colours than the text names) settles whether the model reads the image. The architecture, solution and product prompts have not run live; the lead's planned architecture rerun is the first of those. Neither JPEG, WEBP, several images in one call, nor `--context` has run live.

## Step 4: Two follow-up fixes from the lead's read of the hand-back

**Author:** builder

### Prompt Context

**Verbatim prompt:** "Two small follow-up fixes on branch second-opinion-cost-and-review-modes, as one new commit (same rules: stage by name, no push, no live calls at all this time). 1. Missing usage metadata must not produce a number. When the response has no `usageMetadata` (or no promptTokenCount in it), the cost line must say the price is unknown because the response carried no token usage, and the JSON cost must have usd null and dkk null with a reason. Today it prints 0.0000 USD, which is a wrong number. Add a test. Update the SKILL.md sentence that documents the old behaviour. 2. The sentence \"Line-level bugs in a single file are out of scope unless they show a structural problem\" belongs only in the architecture and solution prompts. Remove it from product and design (my requirement B2 was worded too broadly). Keep \"review at the level of the material\" in all four. Adjust tests if any pin it."
**Interpretation:** Close the two open points I listed in my self-review: a cost of zero for a response with no usage, and a sentence about files in two prompts whose material is not files.
**Inferred intent:** No number that is not backed by token counts, and no instruction in a prompt that does not fit the material it reviews.

### What I did

In `estimate_cost` a response with no `promptTokenCount` now returns before any price lookup: `usd` and `dkk` are null and `reason` says the response carried no token usage. The check comes before the price override, so `--price-in` and `--price-out` do not turn it back into a number. A reported count of 0 is still usage and is still priced; the test holds both sides.

The line-level sentence moved out of the shared prompt frame into a constant that only `architecture` and `solution` get. The test that pinned the sentence in all four prompts now asserts where it is and where it is not, and that removing it left no stray space or double full stop.

SKILL.md: the sentence that documented the zero is replaced, the line about line-level bugs names the two modes, and the note on the live call says that the design prompt has lost one sentence since that call.

`python -m unittest discover -s skills/second-opinion/scripts -v`: 81 tests, OK. The wire-pin test for code mode passed unchanged. No live call.

### Why

A cost of 0.0000 USD next to a usage line of zeros looks like a free call. It is a call nobody could price.

### What worked

Both points were already written down as open in the self-review, so the fix was to act on a known list, not to search.

### What didn't work

Nothing failed in this step.

### What I learned

"Absent" and "zero" are different answers from an API, and `int(x or 0)` erases the difference. The usage line keeps printing zeros for an absent count, as it did before this feature; only the cost line now tells the two apart.

### What was tricky

The one live call ran with the design prompt that still held the removed sentence. The claim "design mode ran live" is therefore true for the earlier wording only, and the documentation has to say that.

### What warrants review

The design and product prompts in their present form: `python skills/second-opinion/scripts/second_opinion.py --mode product --requirements-text x --context CLAUDE.md --dry-run`.

### Future work

The design prompt in its present form has not run live. The call that tests whether the model reads the image (Step 3) would cover it.
